### 1、微软开源Agensh多智能体框架，无中心编排扩展至1024个代理 {#event-242801}

【智能体平台、协议与执行系统】 【微软Agensh】 【多智能体自组织】 【性能提升】

📋 **要点**：2026年10月，微软研究院开源Agensh多智能体框架，取消多数代理框架依赖的中心编排器，每个worker并发异步执行五步循环：读取目标与同伴进展、发布CLAIM认领子任务、本地执行并发布发现、按验收标准验证、合并到共享Git仓库。三个服务连接worker：Gitea托管共享工作区，Mattermost承载团队频道与私信，共享上下文板存储OBSERVED、**FACT**、**FAIL**、CLAIM和PATCH_SUMMARY类型笔记。在ProgramBench五项最难任务上，**GPT-5.6-**sol高推理下128个代理将均值从**19.31%**提升至**28.78%**，**GPT-6.1-**sol下32个代理在pandoc达**79.59%**。
📌 **总结**：Agensh验证了无中心编排的多智能体扩展路径，代理可自组织认领任务、复用可信审查者并标准化集成协议，128个代理带来约**49%**相对提升。对智能体平台与执行系统而言，该架构提示编排瓶颈可通过共享仓库、消息通道和结构化发现板缓解，但token成本未披露，且验证依赖ProgramBench场景，企业落地需评估成本与任务适配性。

## AI推理与服务加速

### 1、SPOT以提交顺序预测为扩散语言模型实现无损投机解码加速 {#event-249016}

【AI推理与服务加速】 【SPOT扩散语言模型投机解码】 【提交顺序预测】 【性能提升】

📋 **要点**：扩散语言模型承诺并行文本生成，但实际面临速度与质量的两难：精确解码每次前向只填充一个掩码位置，多token解码方案则有损。投机解码是自回归模型的标准无损加速手段，但无法直接迁移到扩散语言模型，因为后者必须同时决定生成什么和在哪里生成。研究者指出顺序正是缺失的一环：模型上一轮的预测已在超过**90%**的位置给出正确token，但未给出下一个位置。为此提出SPOT，一个0.62M参数的模型，仅读取目标模型的输出分布来预测提交顺序并构造候选续写树，目标模型通过状态相等在单次前向中验证；耦合噪声匹配在草稿与目标间共享Gumbel噪声，使验证在任意温度下保持精确。实验显示SPOT将目标前向次数最多减少**6.8倍**，在SDAR-**8B**上吞吐达到标准解码的**3.4倍**，并在T=0和T=1下匹配或超过校准与免训练草稿基线；**SPOT-**Sets在动态阈值解码基础上将SDAR-**8B**吞吐平均再提升**59%**，且学习到的草稿器可在六个不同扩散语言模型间迁移。
📌 **总结**：SPOT把投机解码的草稿-验证范式成功移植到扩散语言模型，用轻量顺序预测器解决扩散解码中位置选择这一关键瓶颈，并以耦合噪声匹配保证任意温度下的无损验证。对推理服务架构而言，这意味着扩散语言模型可以复用投机解码式的加速路径，降低目标前向次数与单token成本；草稿器跨六个模型迁移的能力降低了为每个模型单独训练加速组件的成本，为多模型推理平台提供可复用的加速资产。对技术路线判断而言，该工作说明扩散语言模型的速度-质量权衡可通过解码顺序建模而非仅靠模型规模解决，值得纳入推理加速预研方向。
来源：[Hugging Face Papers](https://arxiv.org/abs/2610.22543)
原文标题：On the SPOT: Enhancing Speculative Decoding for Diffusion Language Models via Commit-Order Prediction

### 2、斯坦福与UC Berkeley发布TokenGate，长上下文prefill最快提速11.3倍 {#event-243018}

【AI推理与服务加速】 【TokenGate】 【长上下文prefill加速】 【性能提升】

📋 **要点**：斯坦福和UC Berkeley研究者发布**TokenGate**，一种为预训练LLM增加可学习token剪枝的即插即用模块，论文编号arXiv:2610.26754，代码和检查点以Apache-2.0在GitHub开源。其前向过程分三阶段：门控层以下处理全部N个token，门控层用MLP对每个token打分并通过top-K选择保留高分token，门控层以上仅处理K个token且不为被剪枝token创建KV条目，仅文档部分可剪枝、问题永不剪枝。为解决top-K不可微问题，**TokenGate**借鉴MoE路由器技巧，将保留token的分数作为注意力logits偏置以打通梯度。在Qwen3-**1.7B**上测试RepoBench-P、2WikiMultihopQA、**MultiNews**、BioDEX和**NIAH**，相比全量prefill实现**1.4倍**至**11.3倍**TTFT加速和**1.5倍**至**3.4倍**峰值显存降低，**NIAH** 16k达**11.3倍**加速和**3.42倍**显存节省，128k上下文TTFT增益达**13.0倍**。
📌 **总结**：**TokenGate**把token剪枝从免训练启发式升级为可端到端训练的门控模块，仅需小型MLP门控和LoRA即可为现有LLM增加**长上下文prefill加速**能力，无需从头预训练；其在Qwen3.5-**2B**混合注意力模型上可剪枝Gated DeltaNet层，而FastKV只能剪枝注意力层，为长上下文推理服务降低首token延迟和显存成本提供新的架构选项，对推理引擎和模型服务系统优化有直接工程价值。

### 3、Tesla 联合 Red Hat 用 KServe+llm-d+vLLM 支撑生产推理，前缀缓存路由带来 3 倍吞吐 {#event-242992}

【AI推理与服务加速】 【KServe+llm-d+vLLM】 【前缀缓存感知路由】 【性能提升】

📋 **要点**：**Tesla** 与 **Red Hat** 团队在生产环境中评估 **LLM** 推理规模化难题，指出简单 v**LLM** 加 **Kubernetes StatefulSet** 方案存在网络存储拖慢模型加载、本地卷造成节点与 **Pod** 强绑定、轮询负载均衡无法利用 **GPU KV-cache** 等瓶颈。最终采用 **KServe** 及其 **Inference Gateway Extension** 驱动的 **llm-d** 与 vLLM 组合，通过 **Envoy**、**Envoy** AI Gateway 和 **Gateway API Inference Extension** 实现**前缀缓存感知路由**，把请求定向到持有对应 **KV-cache** 的 vLLM 实例。在 4 张 **AMD MI300X**、tensor-parallel-size=4、gpu-memory-utilization=0.90、max-model-len=65536 配置下服务 **Llama 3.1 70B**，启用该路由后输出 token/s 提升 **3 倍**、**TTFT** 降低 **2 倍**。
📌 **总结**：该实践把**前缀缓存感知路由**从概念验证推进到生产可用，说明在 **GPU** 成本高企的背景下，调度层对 **KV-cache** 的利用可直接转化为吞吐与首 token 延迟收益，对推理服务架构的负载均衡设计具有替代意义。同时 **Tesla** 与 **Red Hat** 把生产边缘问题回馈上游 **KServe**，包括 storageInitializer 可选化与支持最新 **Gateway API Inference Extension**，表明该栈正在通过社区协作硬化，对计划自建大规模 **LLM** 推理平台的团队具备参考价值。

## 模型训练

### 1、Google DeepMind揭示Softmax与交叉熵数值Bug并给出修复方案 {#event-242695}

【模型训练】 【Google DeepMind】 【Softmax数值精度】 【研发效率提升】

📋 **要点**：2026年10月，**Google DeepMind**首席研究科学家Jonathan T. Barron与Dan **Gnanapragasam**、**Michael** Tschannen在arXiv提交论文，指出PyTorch、**JAX**、TensorFlow等主流框架的Softmax与交叉熵标准实现存在两个数值精度Bug。第一个是Softmax **Collapse**，当正确类别Logit Margin超过fp32约16.6的精度悬崖时，正确类别梯度被错误归零，破坏交叉熵梯度之和为零的约束；第二个是Softmax **Cancellation**，在知识蒸馏中学生与教师Logit相同时仍产生非零残余梯度。团队提出将最大Logit项从指数求和中分离并用softplus计算，以及从Logit差值出发在对数空间用expm1和log1p计算概率差，保留原数学定义且无需提高浮点精度。
📌 **总结**：该修复直接作用于深度学习工具链最基础的Softmax与交叉熵实现，无需改变损失函数定义或提升浮点精度即可消除梯度计算错误，有望改善bf16/fp32低精度训练中的损失尖峰与能力退化问题。对AI前沿技术预研规划师而言，这提示基础算子实现仍存在可优化空间，需关注框架层数值稳定性；对技术主管而言，修复方案可低成本替换现有实现，可能提升训练稳定性与研发效率，但大规模**模型训练**中的实际效果仍需验证。
来源：[机器之心](http://mp.weixin.qq.com/s?__biz=MzA3MzI4MjgzMw==&mid=2651069889&idx=1&sn=f243963ab47a3c32471ca7d3319ef4c6&chksm=85edc87fcfb850dadb3686d56e83abaa3f9932f0b222e20f0d1163ffe97737e76f1c427bf5a1&scene=0&xtrack=1#rd)

## AI安全、可信与治理

### 1、清华长三角研究院联合北理工提出 EXISTBENCH，实测 10 款大模型生存性风险 {#event-249133}

### 1、Google DeepMind揭示Softmax与交叉熵数值Bug并给出修复方案 {#event-242695}

【模型训练】 【Google DeepMind】 【Softmax数值精度】 【研发效率提升】

📋 **要点**：2026年10月，**Google DeepMind**首席研究科学家Jonathan T. Barron与Dan **Gnanapragasam**、**Michael** Tschannen在arXiv提交论文，指出PyTorch、**JAX**、TensorFlow等主流框架的Softmax与交叉熵标准实现存在两个数值精度Bug。第一个是Softmax **Collapse**，当正确类别Logit Margin超过fp32约16.6的精度悬崖时，正确类别梯度被错误归零，破坏交叉熵梯度之和为零的约束；第二个是Softmax **Cancellation**，在知识蒸馏中学生与教师Logit相同时仍产生非零残余梯度。团队提出将最大Logit项从指数求和中分离并用softplus计算，以及从Logit差值出发在对数空间用expm1和log1p计算概率差，保留原数学定义且无需提高浮点精度。
📌 **总结**：该修复直接作用于深度学习工具链最基础的Softmax与交叉熵实现，无需改变损失函数定义或提升浮点精度即可消除梯度计算错误，有望改善bf16/fp32低精度训练中的损失尖峰与能力退化问题。对AI前沿技术预研规划师而言，这提示基础算子实现仍存在可优化空间，需关注框架层数值稳定性；对技术主管而言，修复方案可低成本替换现有实现，可能提升训练稳定性与研发效率，但大规模**模型训练**中的实际效果仍需验证。

## AI推理与服务加速

### 1、SPOT以提交顺序预测为扩散语言模型实现无损投机解码加速 {#event-249016}

【AI推理与服务加速】 【SPOT扩散语言模型投机解码】 【提交顺序预测】 【性能提升】

📋 **要点**：扩散语言模型承诺并行文本生成，但实际面临速度与质量的两难：精确解码每次前向只填充一个掩码位置，多token解码方案则有损。投机解码是自回归模型的标准无损加速手段，但无法直接迁移到扩散语言模型，因为后者必须同时决定生成什么和在哪里生成。研究者指出顺序正是缺失的一环：模型上一轮的预测已在超过**90%**的位置给出正确token，但未给出下一个位置。为此提出SPOT，一个0.62M参数的模型，仅读取目标模型的输出分布来预测提交顺序并构造候选续写树，目标模型通过状态相等在单次前向中验证；耦合噪声匹配在草稿与目标间共享Gumbel噪声，使验证在任意温度下保持精确。实验显示SPOT将目标前向次数最多减少**6.8倍**，在SDAR-**8B**上吞吐达到标准解码的**3.4倍**，并在T=0和T=1下匹配或超过校准与免训练草稿基线；**SPOT-**Sets在动态阈值解码基础上将SDAR-**8B**吞吐平均再提升**59%**，且学习到的草稿器可在六个不同扩散语言模型间迁移。
📌 **总结**：SPOT把投机解码的草稿-验证范式成功移植到扩散语言模型，用轻量顺序预测器解决扩散解码中位置选择这一关键瓶颈，并以耦合噪声匹配保证任意温度下的无损验证。对推理服务架构而言，这意味着扩散语言模型可以复用投机解码式的加速路径，降低目标前向次数与单token成本；草稿器跨六个模型迁移的能力降低了为每个模型单独训练加速组件的成本，为多模型推理平台提供可复用的加速资产。对技术路线判断而言，该工作说明扩散语言模型的速度-质量权衡可通过解码顺序建模而非仅靠模型规模解决，值得纳入推理加速预研方向。
来源：[Hugging Face Papers](https://arxiv.org/abs/2610.22543)
原文标题：On the SPOT: Enhancing Speculative Decoding for Diffusion Language Models via Commit-Order Prediction

### 1、Tesla 联合 Red Hat 用 KServe+llm-d+vLLM 支撑生产推理，前缀缓存路由带来 3 倍吞吐 {#event-242992}

【AI推理与服务加速】 【KServe+llm-d+vLLM】 【前缀缓存感知路由】 【性能提升】

📋 **要点**：**Tesla** 与 **Red Hat** 团队在生产环境中评估 **LLM** 推理规模化难题，指出简单 v**LLM** 加 **Kubernetes StatefulSet** 方案存在网络存储拖慢模型加载、本地卷造成节点与 **Pod** 强绑定、轮询负载均衡无法利用 **GPU KV-cache** 等瓶颈。最终采用 **KServe** 及其 **Inference Gateway Extension** 驱动的 **llm-d** 与 vLLM 组合，通过 **Envoy**、**Envoy** AI Gateway 和 **Gateway API Inference Extension** 实现**前缀缓存感知路由**，把请求定向到持有对应 **KV-cache** 的 vLLM 实例。在 4 张 **AMD MI300X**、tensor-parallel-size=4、gpu-memory-utilization=0.90、max-model-len=65536 配置下服务 **Llama 3.1 70B**，启用该路由后输出 token/s 提升 **3 倍**、**TTFT** 降低 **2 倍**。
📌 **总结**：该实践把**前缀缓存感知路由**从概念验证推进到生产可用，说明在 **GPU** 成本高企的背景下，调度层对 **KV-cache** 的利用可直接转化为吞吐与首 token 延迟收益，对推理服务架构的负载均衡设计具有替代意义。同时 **Tesla** 与 **Red Hat** 把生产边缘问题回馈上游 **KServe**，包括 storageInitializer 可选化与支持最新 **Gateway API Inference Extension**，表明该栈正在通过社区协作硬化，对计划自建大规模 **LLM** 推理平台的团队具备参考价值。
