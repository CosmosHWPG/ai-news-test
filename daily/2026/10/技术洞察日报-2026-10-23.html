1、SearchWeaver 自动优化智能体搜索接口，BrowseComp-Plus 准确率从 71.6% 升至 78.4%

智能体平台、协议与执行系统 SearchWeaver 搜索接口优化 研发效率提升

📋 要点：2026年10月21日，arXiv cs.CL发布论文《Let Agents Design How They Search: Automatic Interface Optimization for Agentic Search》，针对现有智能体搜索接口由人工固定、对所有语料统一应用、而有效设计可能依赖语料的问题，提出 SearchWeaver 自动搜索接口优化框架。该框架由提议器利用执行轨迹与任务奖励，联合修订语料工件、可执行工具与使用说明，优化哪些信息预先准备、工具执行哪些操作、哪些决策留给搜索智能体。在 GPT-5.4-nano 上，优化后的接口将 BrowseComp-Plus 答案准确率从 71.6% 提升至 78.4%，在四个 BRIGHT 子集上平均 nDCG@10 从 45.7 提升至 55.0，均优于直接语料交互基线。

📌 总结：该工作把智能体搜索的优化对象从提示词与检索算法扩展到语料工件、工具与使用说明的联合接口设计，证明接口可随语料自动适配并带来准确率与检索质量的双重提升。对智能体平台架构而言，这意味着搜索接口可作为可学习组件纳入运行时，由执行轨迹驱动迭代；对技术主管而言，BrowseComp-Plus 与 BRIGHT 上的可复现数字为评估搜索智能体接口方案提供了基准，但论文基于 GPT-5.4-nano 单一模型，跨模型泛化需进一步验证。

智能体平台、协议与执行系统 ReMAS多智能体红队框架 系统提示提取 安全风险

📋 要点：LLM智能体越来越多地部署在多智能体系统（MAS）中完成复杂任务，但此前的黑盒红队攻击主要针对单智能体，在多智能体系统中效果明显下降，原因是多个子智能体可能不直接与用户交互。为此该研究提出ReMAS，首个面向MAS的强化学习红队框架，通过微调攻击LLM生成有效的对抗提示以提取系统提示。框架分两步：重写阶段优化基础攻击提示以提高提取成功率，模板生成阶段构造攻击模板以提升调用特定子智能体并暴露其系统提示的概率。大量实验表明，该方法相比现有黑盒攻击显著提升攻击成功率，并可在不同后端LLM与MAS结构间迁移。结果凸显多智能体系统的脆弱性以及针对自适应黑盒对手构建更强防御的重要性。

📌 总结：该工作把红队攻击从单智能体扩展到多智能体系统，指出子智能体不直接面向用户这一结构特征会削弱既有黑盒攻击，同时说明经强化学习微调的攻击者可以跨后端模型与MAS拓扑迁移。对Agent平台架构而言，这意味着系统提示不能仅靠单点防护，需要在子智能体调用链、工具路由与上下文隔离层面设计防御；对安全治理而言，其迁移性结论提示防御评估应覆盖自适应对手而非固定攻击集；对产品落地而言，多智能体编排在引入能力增益的同时扩大了提示泄露面，权限与审计设计需前置。

4、Apache RocketMQ 用 LiteTopic 为 MCP 任务建状态账本，解决无状态服务端任务丢失

智能体平台、协议与执行系统 Apache RocketMQ LiteTop… MCP Tasks 状态存储 架构替代

📋 要点：MCP 通过 Tasks 扩展（SEP-2663，状态已 Final）定义异步任务机制，服务端先返回 taskId 句柄，客户端通过 tasks/get 轮询或 notifications/tasks 订阅获取结果，但协议未定义任务状态存储位置；同时 SEP-2575《Make MCP Stateless》要求服务端必须无状态，导致状态放在副本内存时出现换副本查不到、副本宕机丢状态、客户端无法自证三个问题。Apache RocketMQ 在 apache/rocketmq-ai 仓库开源 mcp-tasks-rocketmq，采用 Task as LiteTopic 思路：一个任务对应一条专属 LiteTopic 通道，通道内消息序列即状态账本，提交、执行、查询三步均读写同一通道，单台 Broker 可支撑百万级独立通道并按 TTL 自动回收。

📌 总结：该实现把任务分发与状态存储统一到消息底座，使 MCP 服务端副本可随意重启扩缩，任务不丢、失败可自动重试、执行副本与创建副本解绑、任意副本可应答查询。对Agent平台架构而言，这提供了一条不改协议、只实现官方扩展点的落地路径，也表明消息中间件正从单纯消息通道向Agent协作基础设施演进，对长任务、高并发会话场景的可靠性设计有直接参考价值。
